Three-file leaf module forming the HTTP surface of PhishGuard:
- `runtime_config.py` is imported first and builds a frozen `RuntimeSettings` dataclass from `.env` plus environment variables (`PHISHGUARD_*`, `FLASK_SECRET_KEY`, `RENDER`, `VERCEL`, `FLASK_DEBUG`). It enforces production vs. development defaults (ephemeral secret key in dev, mandatory secret in prod; 5 GiB local upload limit vs. 100 MiB hosted) and exposes the singleton `SETTINGS`.
- `app.py` creates the Flask instance, applies `SETTINGS` into `app.config`, calls `configure_security(app, SETTINGS)` from the `security` package, initializes the SQLite schema via `init_db()` at import time (creating `scans`, `file_scans`, `email_scans`, `security_incidents` tables), and registers all routes: HTML pages (`/`, `/files`, `/email`, `/dashboard`, `/authentication`, `/unlock`), public JSON API (`/api/v1/scan/url`, `/api/files/<id>`, `/api/dashboard/*`), health probes (`/healthz`, `/api/v1/health`, `/api/email/health`), and the docs page (`/api`). Route handlers delegate analysis to sibling packages (`feature_extraction`, `file_analysis`, `email_security`, `soc_dashboard`) and persist results through a `_connection()` context manager wrapping sqlite3 with auto-commit/rollback.
- `wsgi.py` is a one-line re-export of `app.app` so process managers target the stable `wsgi:app` entry point while local dev still runs `python app.py` directly.
Dependency direction is strictly inward: `app.py` depends on `runtime_config` and external feature/security/dashboard modules; `wsgi.py` depends only on `app`; `runtime_config.py` has no intra-app dependencies.
