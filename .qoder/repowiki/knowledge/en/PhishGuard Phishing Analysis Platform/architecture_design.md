The repository is a multi-component application with no single orchestrator package; cross-child wiring happens through environment-driven configuration and shared runtime contracts:
- `requirements.txt` pins the shared dependency graph (Flask, gunicorn, Jinja2, scikit-learn, pandas, dnspython, pypdf, Pillow) consumed by both `flask_backend`, `email_scanner`, and `tests`.
- `.env.example` defines the canonical configuration surface (`FLASK_SECRET_KEY`, `PHISHGUARD_DATA_DIR`, `MAX_UPLOAD_BYTES`, `PHISHGUARD_ACCESS_CODE`, `PHISHGUARD_ALLOWED_ORIGINS`, `PHISHGUARD_RATE_LIMIT`, `FILE_SCAN_WORKERS`, optional ClamAV/VT/OPSWAT keys) that every child reads at startup via `python-dotenv`.
- `Procfile` and `render.yaml` are the unified deployment entry points: both launch `gunicorn --bind 0.0.0.0:$PORT --workers 2 --threads 4 --timeout 120 --access-logfile - wsgi:app`, so Render and any Procfile-capable host run the same WSGI app exposed by `flask_backend`.
- `vercel_frontend` proxies browser requests to the hosted backend, keeping the upstream origin out of client-side code and relying on the same `PHISHGUARD_ALLOWED_ORIGINS` CORS policy enforced by the Flask app.
- Loose scripts at the root (`feature_extraction.py`, `file_analysis.py`, `security.py`, `soc_dashboard.py`) provide ad-hoc analysis utilities that reuse the same data directory and model artifacts produced/consumed by the backend and scanner.
